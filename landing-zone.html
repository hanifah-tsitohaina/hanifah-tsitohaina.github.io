Context

Why a landing zone, and why hub-and-spoke

A landing zone is the base environment a company sets up before deploying any real workload on Azure — the network, the identity model, the guardrails. Getting it wrong is expensive: every workload built on top inherits its mistakes.

I chose the hub-and-spoke pattern because it's the one used in almost every enterprise Azure environment I've come across, including at TAG Heuer, where I worked on migration into an already-established Azure setup rather than designing the foundation itself. Building one from scratch here is my way of understanding the "why" behind decisions I previously just executed.

A hub-and-spoke also maps directly onto real constraints I'd expect at a company like Deloitte's "Sovereign Cloud Switzerland": centralised security and audit points, workloads isolated from each other, and an explicit boundary for where data is allowed to live.

Technical decisions

Choices, and why I made them

Hub-and-spoke over a single flat VNet

A flat network is faster to stand up but every workload shares the same blast radius. Splitting prod and non-prod into separate spokes means a misconfiguration in a test environment can't reach production traffic.

Azure Firewall centralised in the hub, not per-spoke NVAs

One inspection point is easier to audit and cheaper to run than duplicating firewall appliances per spoke — and it matches how the "assessments and audits of existing deployments" requirement I've seen in job postings is usually structured in practice.

Custom RBAC roles instead of built-in Owner/Contributor

Built-in roles are broader than most people actually need. Scoping a custom role to exactly the actions a workload team requires is more work upfront but it's the difference between least-privilege and "it happened to work".

Terraform over ARM/Bicep for this project

I already use Bicep day-to-day for pure-Azure resources; Terraform is the more transferable skill across employers who run multi-cloud or hybrid environments, and it's what I'm certifying on (Terraform Associate).

Region restricted to Switzerland North / West via Azure Policy

Not a real client requirement here, but a deliberate constraint: it mirrors the data-residency conversations that come up for a "Sovereign Cloud Switzerland"-style platform, and it's a good excuse to practise Azure Policy rather than just trusting defaults.

Infrastructure as code

Repository structure

Modules are split by concern so each one can be tested, versioned and reused independently of the environment it's deployed into.

landing-zone/
├── modules/
│   ├── network/        # hub + spoke VNets, peering, subnets, NSGs
│   ├── security/        # Azure Firewall, Bastion, VPN Gateway
│   ├── identity/         # custom RBAC roles, Key Vault, access policies
│   ├── governance/    # Azure Policy definitions & assignments
│   └── monitoring/    # Log Analytics workspace, alert rules, dashboard
├── environments/
│   ├── prod/                # environment-specific tfvars
│   └── nonprod/
├── .github/workflows/
│   └── terraform.yml   # plan on PR, manual approval before apply
└── README.md

Each module exposes only the variables an environment actually needs to override — region, address space, and tags — everything else stays fixed to avoid drift between environments.

Governance & monitoring

Keeping the environment honest

Naming convention
Enforced through Azure Policy — resource type, environment and region encoded in every name (e.g. vnet-hub-prod-chn)
Allowed locations
Switzerland North / Switzerland West only, denied elsewhere at the policy level
Mandatory tags
owner, environment, cost-center — deployments without them are rejected
CI/CD pipeline
GitHub Actions runs terraform plan on every pull request; apply requires a manual approval gate
Monitoring
Centralised Log Analytics workspace in the hub, with alert rules for failed sign-ins and resource health
